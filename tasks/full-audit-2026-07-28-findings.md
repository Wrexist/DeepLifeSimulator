### 🟠 `GL-1` — Event chains never complete — activeEventChain latches forever and locks out every future chain

**Anchor:** `contexts/game/GameActionsContext.tsx:2894` · **Severity:** high · **Effort:** S · **Domain:** Game logic correctness — weekly tick ordering, event engine/chains, careers & education, relationships/marriage, disease/death, crime/jail, ambitions/prestige/retirement

**What is wrong.** Verified. `resolveEvent`'s chain block (GameActionsContext.tsx:2887-2921) branches on `currentChain.currentStage`, which is the index of the PREVIOUSLY resolved stage: the new-chain branch (:2914-2921) sets `currentStage: 0` when stage 0 is resolved, and every later resolve does `currentStage + 1`. So after resolving the final stage of an N-stage chain, currentStage === N-2 and the guard `currentStage < totalStages - 1` (:2894) is still true — the ADVANCE branch runs and the COMPLETE branch (:2899-2911, which sets `updatedActiveEventChain = undefined` and pushes the `{completed:true}` entry) is unreachable in normal play. Completion would need an (N+1)th resolve, but lib/events/engine.ts:3071-3072 returns null once `active.currentStage + 1 >= chain.stages.length`, so no further stage is ever generated. From then on engine.ts:3316 finds an activeEventChain but no chain event, and engine.ts:3327 `if (!state.activeEventChain && ...)` is false forever, so `rollEventChain` (engine.ts:3038) can never fire again. `activeEventChain` is written ONLY at GameActionsContext.tsx:2966 (repo-wide grep) — nothing else clears it, and utils/saveValidation.ts has no chain repair, so the latch persists across saves until a prestige reset. Note the earlier hardening actually caused this: with the old hardcoded `totalStages: 3`, the 4-stage `business_opportunity` chain (engine.ts:2871-2960, four stage functions with chainStage 0/1/2/3) DID hit the complete branch on its 4th resolve; switching to `getEventChainStageCount(...)` (engine.ts:3085) made totalStages correct and completion unreachable for all three chains.

**Repro.** Complete any chain, e.g. health_scare (3 stages, engine.ts:2787-2869). Resolve stage 0 → activeEventChain {currentStage:0,totalStages:3}. Resolve stage 1 → currentStage:1. Resolve stage 2 (final) → 1 < 2, so it advances to currentStage:2 instead of completing. Next tick: getNextChainEvent → nextStage 3 >= 3 → null; engine.ts:3327 `!state.activeEventChain` is false. No chain ever rolls again for the rest of that life, and eventChains stays empty.

**Fix.** Two edits. (1) contexts/game/GameActionsContext.tsx:2891-2913 — branch on the stage being resolved, not the stored one: `const resolvedStage = typeof event.chainStage === 'number' ? event.chainStage : currentChain.currentStage + 1; if (resolvedStage < currentChain.totalStages - 1) { updatedActiveEventChain = { ...currentChain, eventId, currentStage: resolvedStage }; } else { updatedActiveEventChain = undefined; updatedEventChains = [...updatedEventChains, { chainId: event.chainId, currentStage: currentChain.totalStages - 1, stages: [], completed: true }].slice(-50); }`. (2) Self-heal already-latched saves without a STATE_VERSION bump: in the weekly tick where `applyWeeklyEvents` runs (GameActionsContext.tsx:1150), or inside `rollWeeklyEvents` at lib/events/engine.ts:3316, when `state.activeEventChain` exists and `getNextChainEvent(state)` returns null, clear the field and append the completed entry — that is exactly the terminal condition and it fixes both live saves and any future off-by-one. Regression test: drive all 3 `health_scare` stages through `resolveEvent` and assert `activeEventChain === undefined` and `eventChains` contains `{chainId:'health_scare', completed:true}`; lib/events/__tests__/eventChains.test.ts only exercises `getNextChainEvent` branching (it hand-builds `activeEventChain` with `totalStages: 4`, test file lines 33-42) and never calls resolveEvent, which is why this survived.

**Risk of the fix.** Behavioural change is confined to chain bookkeeping. The self-heal in (2) will clear latched chains on existing saves the first tick after the update — players mid-chain at the moment of upgrade lose the remainder of that chain (acceptable; they are already stuck). eventChains now actually populates, so its dedupe at engine.ts:3042 starts having effect: a chain completed once will no longer re-roll — intended, but it changes long-run event mix and could shift any subsystem snapshot that pins weekly event output.

**Verification evidence.** Read GameActionsContext.tsx:2887-2921 (advance/complete branch, new-chain branch sets currentStage 0), engine.ts:3038-3055 (rollEventChain early-returns on any activeEventChain), engine.ts:3065-3074 (getNextChainEvent returns null at nextStage >= stages.length), engine.ts:3310-3335 (chain continuation then `!state.activeEventChain` gate), engine.ts:3085 getEventChainStageCount, engine.ts:2786-2970 (3/4/3 stage definitions), and grep showing activeEventChain is written only at GameActionsContext.tsx:2966 with no repair/migration touching it.

### 🟠 `PERF-1` — Save backups are never created in production builds — createBackup rejects the raw-state payload createBackupFromState hands it

**Anchor:** `utils/saveBackup.ts:570 → :425 → utils/saveValidation.ts:1723` · **Severity:** high · **Effort:** S · **Domain:** Performance & code health — weekly tick, render paths, save-path latency, duplication/dead-code/type-escape defect risk

**What is wrong.** `createBackupFromState` (utils/saveBackup.ts:564-577) does `const data = JSON.stringify(state)` — a RAW GameState, not a v2 envelope — and passes it to `createBackup` (line 572). `createBackup`'s first statement is `normalizeBackupPayload(data)` (line 425), which calls `decodePersistedSaveEnvelope(rawSaveData, { allowLegacy: shouldAllowUnsignedLegacySaves() })` (line 90). In `decodePersistedSaveEnvelope` the raw state has no `v === 2`, so control reaches `if (!allowLegacy) return { valid: false, error: 'Unsigned legacy save format is not accepted' }` (utils/saveValidation.ts:1723-1725) BEFORE the `looksLikeLegacySavePayload` shape check. `normalizeBackupPayload` then throws (line 91-93). `createBackup`'s catch only special-cases QuotaExceeded (line 456), so it falls through to `logger.error('Failed to create backup for slot N')` and `return null` (556-557) — it never rejects, so the `.catch` at contexts/game/GameActionsContext.tsx:278 never fires and the save path reports success. `allowLegacy` is false in every shipped build: utils/saveSigningConfig.ts:64-67 sets `allowUnsignedLegacySaves = isDev || EXPO_PUBLIC_ALLOW_UNSIGNED_LEGACY_SAVES === 'true'`, and scripts/preflightSaveSigning.js:34-36 hard-errors if that env var is true for production signed saves. In dev (`__DEV__` true) the legacy branch is taken and everything works, which is why it has never been observed locally. Both production call sites are affected: the per-save backup at contexts/game/GameActionsContext.tsx:277 (every nextWeek + every 2-min autosave) and the pre-onboarding backup at app/(onboarding)/Perks.tsx:491 (via src/features/onboarding/gameInitializer.ts:169).

**Repro.** Build with `__DEV__ === false` / NODE_ENV=production and EXPO_PUBLIC_ALLOW_UNSIGNED_LEGACY_SAVES unset (the shipping config that preflightSaveSigning.js enforces), start a life, tap Next Week. `normalizeBackupPayload` throws 'Unsigned legacy save format is not accepted', `createBackup` logs and returns null, and `listBackups(slot)` returns [] forever. Save itself succeeds, so there is no user-visible symptom until a save corrupts.

**Fix.** In `createBackupFromState` (utils/saveBackup.ts:564-577), wrap before handing off: `const { createSaveEnvelope } = await import('@/utils/saveValidation'); const data = createSaveEnvelope(JSON.stringify(state));` then `return createBackup(slot, data, '', reason)` — `normalizeBackupPayload` then takes the v2 branch at saveValidation.ts:1703 and verifies normally. (Preferred alternative, which also fixes PERF-3: give `normalizeBackupPayload` an overload that accepts an already-decoded in-memory state object and skips the decode/re-parse entirely.) Also drop the now-dead `_checksum` parameter from `createBackup`'s signature (line 421) rather than leaving a parameter the body ignores. Add a real, unmocked test — nothing today exercises the implementation: `__tests__/save/currentSlotSync.test.ts:70` and `__tests__/onboarding/gameInitializer.test.ts:90` both `jest.fn()` it away, and `grep -rl saveBackup __tests__/` returns only that one file. The new test must force production signing (`resolveSaveSigningRuntimeConfig(env, /* explicitIsDev */ false)` with `EXPO_PUBLIC_ALLOW_UNSIGNED_LEGACY_SAVES` unset) and assert `createBackupFromState` → `listBackups(slot).length === 1` → `loadBackup(id)` round-trips.

**Risk of the fix.** Downgraded from critical: the primary save path (utils/saveQueue.ts) is unaffected, so no live data is lost — what is lost is the entire recovery tier, silently, on 100% of shipped builds. Fix risk: switching to a v2 envelope changes what `backup.data` contains, so the restore paths that already decode it (saveBackup.ts:666, GameActionsContext.tsx:3493) keep working, but any dev-machine backups written in the legacy shape must still decode — keep the legacy branch reachable in `normalizeBackupPayload` for reads. Adding a production-config test may need `resolveSaveSigningRuntimeConfig`'s explicit-isDev override to avoid leaking ambient env into the rest of the suite.

**Verification evidence.** Read utils/saveBackup.ts:89-98 (normalizeBackupPayload throws on !decoded.valid), :418-431 (createBackup calls it first; `_checksum` unused, checksum recomputed at :426), :454-457 and :556-557 (catch is QuotaExceeded-only, otherwise logs and returns null), :564-577 (createBackupFromState stringifies raw state). Read utils/saveValidation.ts:1694-1738 — the `!allowLegacy` early return at :1723 precedes any shape check — and :103-105 (`shouldAllowUnsignedLegacySaves` returns the module-level ALLOW_UNSIGNED_LEGACY_SAVES). Read utils/saveSigningConfig.ts:64-67 and scripts/preflightSaveSigning.js:34-36. Confirmed the consumer side is live: utils/saveBackup.ts:666-670 (restoreFromBackup) and contexts/game/GameActionsContext.tsx:3484-3506 (corrupt-save fallback reads listBackups/loadBackup). Grep confirms only two production callers of createBackupFromState (GameActionsContext.tsx:277, Perks.tsx:491) plus the alias `createBackupBeforeMajorAction` at saveBackup.ts:953.

### 🟠 `econ-1` — Luxury sale refund is a flat 60% of CATALOG price while net worth values the same holding at currentValue × 0.6 × conditionMultiplier — selling a damaged or depreciated trophy is a one-tap net-worth (and prestige-point) gain

**Anchor:** `contexts/game/actions/LuxuryActions.ts:155` · **Severity:** high · **Effort:** M · **Domain:** economy

**What is wrong.** Two different answers to "what is this worth" exist and the sell path uses the wrong one. `sellLuxuryItem` computes `const refund = getLuxuryResaleValue(item)` (LuxuryActions.ts:155), which is `Math.floor(item.price * LUXURY_RESALE_FRACTION)` — sticker × 0.6, ignoring the holding entirely (lib/luxury/operations.ts:73-75, LUXURY_RESALE_FRACTION = 0.6 at catalog.ts:257). Net worth uses `getTotalLuxuryMarketValue` (operations.ts:246-259), which is `floor(getHoldingValue(item, holding) * 0.6 * conditionValueMultiplier(getCondition(holding)))`. `conditionValueMultiplier` floors at 0.45 (risk.ts:105-107) and `getHoldingValue` returns the appreciated/depreciated `holding.currentValue` (operations.ts:234-237). So whenever condition < 100 or currentValue < price, cash-on-sale strictly exceeds the market value the item was carrying, and net worth RISES on sale. That figure is live: `netWorth()` in lib/progress/achievements.ts:159 reads `getTotalLuxuryMarketValue(state.luxuryItems, state.luxuryHoldings)`, `executePrestige` reads `netWorth(gameState)` (prestigeExecution.ts:27), and `calculatePrestigePoints` awards `Math.max(0, Math.floor(netWorth / 1_000_000) * 100)` (prestigePoints.ts:42). Two knock-on consequences confirmed by the same read: (a) appreciation can never be realised — `rare_watch_collection` (+0.10%/wk, catalog.ts:113) shows gains in net worth and still sells for 0.6 × sticker; (b) the entire Phase-5 risk system has no cash consequence on exit, so the INSURANCE_MARGIN docstring's claim that insuring is "a genuine call" (risk.ts:38-47) is false in cash terms. `applyLuxuryRiskForWeek` does run every tick (applyLuxuryItems.ts:114), so damaged condition is reachable in normal play.

**Repro.** Own `private_jet` ($65,000,000, appreciation -0.06%/wk, catalog.ts:194-199). No incident needed: after ~200 weeks `holding.currentValue` ≈ $57.2M, so the net-worth contribution is floor(57.2M × 0.6 × 1.0) ≈ $34.3M. Tap Sell → `refund = floor(65,000,000 × 0.6) = $39,000,000` cash. Net worth is ~$4.7M higher for one tap (+470 prestige points). With damage the gap is larger: `mega_yacht` ($300M) at condition 0 carries 0.6 × 0.45 = 0.27 × value in net worth but pays 0.6 × price in cash — a swing of ~0.33 × $300M ≈ $99M ≈ +9,900 prestige points. Sell-everything-then-prestige is already a natural player action, so this is not an obscure path.

**Fix.** 1) Factor the per-item valuation term out of `getTotalLuxuryMarketValue` (lib/luxury/operations.ts:250-259) into an exported `getLuxuryHoldingValue(item, holding)` = `Math.floor(getHoldingValue(item, holding) * LUXURY_RESALE_FRACTION * conditionValueMultiplier(getCondition(holding)))`, and have `getTotalLuxuryMarketValue` reduce over it so the two definitions physically cannot drift again. 2) In `sellLuxuryItem` (contexts/game/actions/LuxuryActions.ts:137-186) replace line 155 with `const refund = getLuxuryHoldingValue(item, gameState.luxuryHoldings?.[itemId])` AND recompute it inside the `setGameState(prev => …)` updater from `prev.luxuryHoldings?.[itemId]` before calling `applyMoneyDelta` (line 161), so the credit uses fresh state like every other atomic action here; keep the outer value only for the toast at line 184. 3) Mirror it at the four UI read sites so the quote matches the payout: components/computer/LuxuryApp.tsx:255 (card), :508 (post-sell toast), :635 (detail sheet) and :1020 (confirm sheet — it also divides by `pendingSell.price` to show a percentage, which must become percentage-of-holding-value). 4) Leave `getTotalLuxuryResaleValue` (ids-only) alone but stop using it where holdings ARE available: LuxuryApp.tsx:384 `collectionValue` should call `getTotalLuxuryMarketValue(ownedIds, gameState.luxuryHoldings)`. 5) Add tests: sell proceeds == the item's net-worth contribution immediately before the sale (net-worth-neutral), and a damaged item sells for strictly less than a pristine one.

**Risk of the fix.** lib/luxury/__tests__/luxury.test.ts:100 pins `getLuxuryResaleValue(item) === floor(price * LUXURY_RESALE_FRACTION)` and :150 asserts the sell refund is exactly `floor(250_000 * 0.6)`; yieldAppreciation.test.ts:163 pins `getTotalLuxuryMarketValue([id], {}) === floor(price * fraction)` (still true for a pristine holding, so that one should survive). __tests__/refactor/subsystemEquivalence.test.ts snapshots may cover the sell path. Player-facing nerf: damaged items now sell for less. Cross-domain dependency — the stability auditor's reach-2 shows `setLuxuryInsurance`/`restoreLuxuryItem` currently have zero call sites, so shipping this fix ALONE turns every incident into unavoidable permanent loss with no counterplay. Land it together with wiring Restore/Insure into LuxuryApp, or the nerf lands without its mitigation. lib/devtools/simulations.ts:417 also uses the ids-only helper; harmless, but don't let it be read as the canonical value.

**Verification evidence.** Read LuxuryActions.ts:137-186 (refund computed once at :155 from the catalog item, never from `prev.luxuryHoldings`, credited via applyMoneyDelta at :161); operations.ts:73-75 and :234-259 (two divergent valuations, the market one condition- and appreciation-aware); risk.ts:93-107 (getCondition/conditionValueMultiplier, 0.45 floor); applyLuxuryItems.ts:109-125 (appreciation + risk both run every tick and mutate holdings); achievements.ts:159 (netWorth counts luxury at market value); prestigePoints.ts:42 + prestigeExecution.ts:27 (100 pts per $1M of that netWorth). tasks/lessons.md:525 independently confirms `netWorth()` in achievements.ts is the canonical one prestige reads. Nothing in tasks/*.md records a fix for the sell-side valuation.

### 🟠 `reach-2` — Luxury insurance and restoration have zero call sites, so the weekly risk roll is one-way, permanent value destruction with no counterplay

**What is wrong.** Verified: `setLuxuryInsurance` (LuxuryActions.ts:361) and `restoreLuxuryItem` (LuxuryActions.ts:398) are exported and complete (both re-check inside the `setGameState` updater; restore routes through `applyMoneyDelta`), and a repo-wide grep for either identifier returns ONLY their two definition lines — no importer anywhere. `components/computer/LuxuryApp.tsx:90` imports exactly `hostLuxuryEvent, performLuxuryVerb, purchaseLuxuryItem, sellLuxuryItem`. **Repro.** Own the racehorse (weeklyChance 0.010, severity 45 per RISK_BY_ID in lib/luxury/risk.ts).
