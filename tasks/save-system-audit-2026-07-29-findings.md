# Save-system audit — 2026-07-29

Five Opus 5 audit domains, each finding adversarially verified by an independent Opus 5 verifier, synthesised by Fable 5. **46 raw findings → 42 confirmed, 11 refuted.**

Anchored on a real player report: a prestiged save replaced by a fresh Week 1 / Age 18 / Generation 1 character that validated clean (0 errors, 0 warnings, no error or warn logs). App 2.5.3 build 141, state version 20, iOS 26.5.2, production.


## Verdict on the reported incident

**SAVE-OW-1 — Pristine boot state autosaved over the active slot from the main menu — this is the incident, and it was fixed in 2.5.7**

GameProvider mounts inside AppProviders, which wraps expo-router's <Slot> at app boot, so both the 2-minute periodic autosave (GameActionsContext.tsx:3414-3436) and the AppState background/inactive force-save (:3257-3304) run while the player is still on MainMenu with gameState === initialGameState and currentSlot === 1 (GameStateContext.tsx:38,41). On builds before 2.5.7 there was no content guard, so those saves wrote the untouched default into slot 1, set lastSlot=1 (utils/saveQueue.ts:240-241, :404-406) and refreshed the slot-meta cache. The state is legitimately valid, so validation reports 0 errors, and the only log line is logger.info('Game save queued successfully') — nothing at error or warn level. Note the second, equally destructive shape: if the player's real save was in slot 2 or 3, the pristine write lands in slot 1 AND repoints lastSlot to 1, so Continue loads the phantom while the real save is still on disk — which is exactly what 'seems to have been overwritten by a fresh new game' looks like from the outside.

*Evidence:* The diagnostic fingerprint matches contexts/game/initialState.ts field-for-field: money 200 (:23), age 18 / year 2025 / month January / week 1 (:120-121), weeksLived 0 (:75), generationNumber 1 (:103), careers = INITIAL_CAREERS which has 30 entries (:732 + lib/careers/careerData.ts), items 8 (:734ff), relationships 2 — 'parent1'/'parent2' (:1018ff). It cannot be an onboarding-built state: src/features/onboarding/scenarioData.ts has no scenario starting at age 18 with cash 200 (the only cash:200 scenario starts at age 25, line 110), and buildNewGameState always writes a firstName/lastName and a scenarioId. git show 669c334 ('Fix phantom "Unnamed Character" save appearing on clean installs', 2026-07-19) adds the guard and bumps package.json to 2.5.7, so the player's 2.5.3 build predates it. One detail I could NOT reconcile: the report says State version 20, while STATE_VERSION was already 22 by 2026-07-14 (0403cef) — the repo history here is squashed and never contains a 2.5.3/2.5.4 bump, so either the phantom blob was written by an older build than the reported binary, or the diagnostic reads the blob's stamped version. I checked and ruled out the obvious alternative: runMigrations (utils/saveMigrations.ts:758-798) mutates in place and returns the same object, so loadGame discarding migrationResult.state (GameActionsContext.tsx:3561) is NOT a silent migration loss.

*Repro:* Cold-launch a build <=2.5.6 with a deep save in slot 1. Sit on MainMenu for >2 minutes, or background the app from MainMenu. The autosave/background force-save writes initialGameState to slot 1 and sets lastSlot=1. Relaunch: Continue loads a week-1, age-18, $200, generation-1, prestige-0 game with zero validation errors and no error/warn log line.

#### BRC-1b — restoreFromBackup writes to the LEGACY single key while loadGame reads the double buffer — a restore is a silent no-op on every production build

- **Still present:** `yes-current-tree` · **Explains incident:** no · **Effort:** S
- **Anchor:** utils/saveBackup.ts:728-733 (atomicSave to `save_slot_${slot}`), utils/saveValidation.ts:1840-1878 (atomicSave), :1986-2040 (doubleBufferLoad), contexts/game/GameActionsContext.tsx:3492

NEW — found while verifying BRC-14, and it invalidates BRC-1's fix as written. `restoreFromBackup` restores via `atomicSave('save_slot_' + slot, canonicalBackupData)`; `atomicSave` writes a temp key then `storage.setItem(key, data)` — the plain legacy key only (saveValidation.ts:1865-1878). **Risk.** None to current behaviour — the function has no callers today. It is a hard prerequisite for BRC-1.

#### PIPE-1 — `readSaveSlot` collapses "slot empty" and "slot present but unreadable/unread" into the same `null`, so `findFirstEmptySlot` hands the player's occupied slot to New Game

- **Anchor:** utils/saveValidation.ts:1972-2055 (doubleBufferLoad), :2035 + :2054 (`return { data: null, source: 'none' }`), :2061-2072 (readSaveSlot); src/features/onboarding/saveSlotHelpers.ts:66-67, :71-72, :103-104, :108-110; app/(onboarding)/MainMenu.tsx:541; src/features/onboarding/gameInitializer.ts:169-175

The repo already knows this exact hazard and documents it in the sibling helper: `utils/saveSlotMeta.ts:157-160` says `readSaveSlot` "swallows storage errors into null, which would make a transient failure indistinguishable from a truly empty slot. One correction to the original finding: its claim that SaveSlots is safe is right — I checked. `SaveSlots.tsx:504-515` disables the primary button and relabels it "Delete Slot to Continue" when `selectedCard.error && !hasData`, and :185-190 uses the raw probe. MainMenu is the only unguarded entry.

**Fix.** Three edits, all additive.
(1) utils/saveValidation.ts:1972 — widen `doubleBufferLoad`'s return to `source: 'A'|'B'|'legacy'|'none'|'unverified'|'unknown'`: return `'unverified'` where it currently falls through after `[DOUBLE_BUFFER] Both buffers failed verification` (:2015), and `'unknown'` from the outer `catch` (:2042-2053). Add `export async function readSaveSlotStatus(slot): Promise<'empty'|'unverified'|'unknown'|'ok'>` beside `readSaveSlot` (:2061) that maps those through. `readSaveSlot` itself keeps its current signature so the ~10 existing callers are untouched.
(2) src/features/onboarding/saveSlotHelpers.ts:66-67 — replace `const data = await readSaveSlot(...); if (!data) return i;` with `const status = await readSaveSlotStatus(i); if (status !== 'empty' && status !== 'ok') continue;` and only fall through to the decode when there is data. Mirror at :103-104 so `checkIfAllSlotsFull` counts `'unverified'`/`'unknown'` toward `fullSlots`. `utils/saveSlotMeta.ts:161 probeSaveSlotBlob` is the cheaper drop-in if you prefer not to touch `doubleBufferLoad` — `probe !== 'empty'` ⇒ skip the slot — and it is already the pattern SaveSlots uses.
(3) app/(onboarding)/MainMenu.tsx:541-548 — when `findFirstEmptySlot()` returns null, distinguish "3 real saves" from "a slot needs recovery" and route the latter to `/(onboarding)/SaveSlots` (which already renders 'Recovery Needed' + Delete) instead of the dead-end "All Save Slots Full" alert.
Separately worth doing while in there: `src/features/onboarding/gameInitializer.ts:169` backs up `newState`, not the slot's existing contents — make it snapshot the outgoing blob (or refuse to write a slot whose status is not `'empty'`) so an overwrite is recoverable at all.

**Risk.** Low. Strictly shrinks the set of slots eligible for overwrite. Worst case a genuinely empty slot is misread as occupied, which fails safe (player is sent to SaveSlots to delete it explicitly). Do NOT change `readSaveSlot`'s existing signature — ErrorBoundary.tsx:208/281/372/491, IAPService.ts:1327, saveBackup.ts:706/784 and gameEntryValidation.ts:251 all depend on the current null-on-anything behaviour.

#### SEC-1 — "Could not verify/read" is encoded as the same `null` as "slot is empty", and all three new-game slot guards — including the brand-new last line of defence — read that null as "free to overwrite"

- **Still present:** `yes-current-tree` · **Explains incident:** partly · **Effort:** M
- **Anchor:** utils/saveValidation.ts:1996-2042 + :2065-2072 (doubleBufferLoad/readSaveSlot); src/features/onboarding/saveSlotHelpers.ts:67 and :104; src/features/onboarding/slotSafety.ts:97-98 (UNCOMMITTED, new); utils/saveSlotMeta.ts:204-208; app/(onboarding)/MainMenu.tsx:374-379, :541

`doubleBufferLoad` returns `{ data: null, source: 'none' }` at saveValidation.ts:2042 when both buffers exist but fail `decodePersistedSaveEnvelope`, and again at :2057 when the whole read THREW. `readSaveSlot` (:2070-2071) forwards only `.data`, so the caller cannot tell "nothing stored" from "stored but unverifiable" from "storage read failed". Three consumers then treat null as free: `findFirstEmptySlot` (`if (!data) return i; // nothing stored → safe to use`, saveSlotHelpers.ts:67), `checkIfAllSlotsFull` (`if (!data) continue`, :104), and — the one the previous auditor missed — the uncommitted `slotSafety.inspectSlotForNewLife` (`if (!data) return { status: 'free' }`, slotSafety.ts:98), which `gameInitializer.initializeAndSaveGame` consults at Step 0 immediately before `forceSave` and whose own header says "Any failure to read resolves to `unreadable`, never `free`". Its `unreadable` branch at :101 is unreachable for exactly the same reason the comment at saveSlotHelpers.ts:71-72 is unreachable: the decode that would have failed already happened inside `readSaveSlot`, and its failure was flattened to null. Two independent triggers, neither needing a malicious actor: (a) HMAC/checksum verification failure (key change, SEC-2/SEC-3), (b) a swallowed storage error — saveValidation.ts:28 returns null when the AsyncStorage module fails to load and latches that for the process (`_loadAttempted`, :13-24), and doubleBufferLoad's catch at :2043 swallows any throw. **Fix.** Three specific edits. Add a sibling `readSaveSlotDetailed(slot, storage, options)` returning that object; leave `readSaveSlot` as-is so existing callers do not change meaning. (2) src/features/onboarding/slotSafety.ts:97-98 — this is the one that must land first, since it gates the write: use the detailed read (or, cheaper, `await import('@/utils/saveSlotMeta').then(m => m.probeSaveSlotBlob(slot))` — it must be a DYNAMIC import, because saveSlotMeta.ts:29 statically imports saveSlotHelpers and a static edge back would create a require cycle into the save pipeline) and return `{ status: 'free' }` only when the probe says 'empty'; 'exists' and 'unknown' → `{ status: 'unreadable' }`, which `resolveNewLifeSlot` already turns into a refusal with the right copy (:152-159). (3) src/features/onboarding/saveSlotHelpers.ts:67 and :104 — same probe: only a confirmed 'empty' may be returned by `findFirstEmptySlot`; 'exists'/'unknown' must `continue` (and must count toward `fullSlots` in `checkIfAllSlotsFull`). Then delete the now-genuinely-reachable-or-dead comments at :71-72 accordingly. Separately, MainMenu.tsx:379: when `ensureSaveSlotMeta` returns null, probe before calling `clearSave()` — 'exists'/'unknown' should render a "save needs recovery" Continue card, not no card.

**Risk.** Low. Additive status on the read plus reuse of an existing, already-shipped helper. Two things to watch: a genuinely empty install must still return 'empty' so new players land in slot 1 (probeSaveSlotBlob does); and the dynamic-import direction must be preserved or you create a saveSlotHelpers↔saveSlotMeta require cycle.

#### SEC-8 — The hand-rolled SHA-256 writes a wrong 64-bit length block for EVERY message, not just large ones — the previous finding's "only ≥ 2 MiB" threshold is wrong, and acting on it would orphan every save on every device

- **Still present:** `yes-current-tree` · **Explains incident:** no · **Effort:** S
- **Anchor:** utils/saveValidation.ts:148-152 (`for (let i = 56; i >= 0; i -= 8) bytes.push((bitLen >>> i) & 0xff);`); MAX_SAVE_SIZE at lib/config/gameConstants.ts:170

The defect is real: JS `>>>` masks the shift count to 5 bits, so `bitLen>>>56` is `>>>24`, `>>>48` is `>>>16`, `>>>40` is `>>>8`, `>>>32` is `>>>0` — the eight length bytes come out as [b3,b2,b1,b0,b3,b2,b1,b0] instead of [0,0,0,0,b3,b2,b1,b0]. But the previous finding's analysis is WRONG and dangerously so: it claims the high half is only nonzero at bitLen ≥ 2^24 (≥ 2 MiB) and that a 1 MB string matches node's crypto. It does not. The duplicated low word lands in the HIGH four bytes, which standard SHA-256 requires to be zero for any message under 2^32 bits — so the digest diverges for every message whose bit length is not a multiple of 2^32, i.e. everything except the empty string. I ran the exact function from :124-186 against `crypto.createHmac`/`createHash` for lengths 1, 10, 31, 32, 33, 64, 100, 1000, 1 MiB and 3 MiB: DIFFER at every single one. Consequences: (a) this is self-consistent, so it signs and verifies fine and is NOT a data-loss bug today; (b) it is not HMAC-SHA256, so `lib/progress/cloud.ts`'s `hash`/`signature` (built at services/CloudSyncService.ts:110-115) will disagree with any standards-compliant server for ALL saves, not just big ones; (c) most importantly, the previously-proposed "one-line fix, will invalidate signatures for saves ≥ 2 MiB" would in fact invalidate EVERY save signature on EVERY device — self-inflicting exactly the SEC-2 catastrophe this audit exists to prevent.

**Fix.** utils/saveValidation.ts:151-152 — replace the loop with four explicit zero bytes followed by the four big-endian bytes of `bitLen` (`bytes.push(0,0,0,0, (bitLen>>>24)&0xff, (bitLen>>>16)&0xff, (bitLen>>>8)&0xff, bitLen&0xff)`). This MUST NOT ship alone. Sequence it: (1) land SEC-2's verification-key/algorithm-fallback list first; (2) register the current function as a legacy verifier (keep it under a name like `sha256LegacyPadding`) so existing envelopes still verify; (3) sign new writes with the corrected implementation and let each save re-sign on its next write; (4) only remove the legacy verifier after a release cycle in which every active install has re-saved. Also worth doing while there: the HMAC compare at :1690 is a plain `!==` — irrelevant against a local attacker who already holds the bundled key, so do not spend effort on constant-time here.

**Risk.** HIGH if shipped alone — it changes the digest for 100% of saves, not the ~0% the earlier analysis assumed. Zero risk if landed behind SEC-2's fallback-verify path as sequenced above.
