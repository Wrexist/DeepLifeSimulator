### Section B — P1: Likely Bug

| # | File:Line | Severity | Root Cause | Suggested Fix |
|---|-----------|----------|------------|---------------|
| B1 | `contexts/game/GameActionsContext.tsx:1587` | **P1** | `stateUpdateError` is checked synchronously after `setGameState(...)` at line 1582. But `setGameState` is asynchronous in React 19 concurrent mode — the updater may not have run by the time line 1587 executes, so `stateUpdateError` is still `null`. The error check is therefore unreliable: a real state update error will be silently swallowed and the week proceeds as normal (on the next tick) with stale state. | The correct pattern is to read the error from the state object returned by the updater (pass it as a field in the returned state, e.g. `_weekProgressionError: true`), then check it after the `await new Promise(resolve => setTimeout(resolve, 50))` poll at line 1637 where the state is confirmed via `gameStateRef.current`. |
| B2 | `contexts/game/GameActionsContext.tsx:355–1582` | **P1** | `pendingNotifications` is a plain array declared outside the `setGameState` updater. React StrictMode invokes the updater twice; both invocations mutate `ctx.notifications` (passed by reference) via `.push()` inside `applyRelationshipHealth`, `applyCrimeTick`, `applyVehiclesForWeek`, etc. The outer code at line 1603 deduplicates by `id`, but several notification IDs are dynamic (e.g. `vehicle-accident-${v.id}`, `spark-tick-${nextWeeksLived}-${pendingNotifications.length}`) — the length-based suffix changes between the two invocations so both copies survive the dedup and the user sees duplicate toasts. | Use stable, content-addressed IDs (e.g. `spark-tick-${nextWeeksLived}-${sparkType}`) rather than `pendingNotifications.length`-based suffixes. For the vehicle accident notification, the `v.id`-based ID is already stable — that one is fine. |
| B3 | `contexts/game/actions/JobActions.ts:119` | **P1** | `gameState.crimeSkills[job.skill]?.level` — `crimeSkills` is typed as an object literal with fixed keys (pickpocketing, forgery, etc.). If a legacy save or a future schema change introduces an unknown `job.skill` string, the optional-chain falls through to `0` which is correct. But `gameState.crimeSkills` itself can be `undefined` on a legacy save that pre-dates the field. Line 119 does NOT guard `gameState.crimeSkills?.`, only `[job.skill]?.level`, so if `crimeSkills` is entirely absent the expression throws `TypeError: Cannot read properties of undefined (reading 'undefined')`. `repairGameState` may fill this in on load, but any path that skips repair (direct `setGameState` assignments) exposes this. | Change line 119 to `(gameState.crimeSkills?.[job.skill]?.level || 0) * 5`. |
| B4 | `contexts/game/actions/JobActions.ts:458` | **P1** | `gainCrimeSkillXp`: `prev.crimeSkills[skillId]` — same missing `?.` as B3. If `crimeSkills` is absent from the state object (legacy save not yet repaired), this throws, crashing any crime-skill XP gain including the street-job path. | Change to `prev.crimeSkills?.[skillId]`. |
| B5 | `contexts/game/GameActionsContext.tsx:2238` | **P1** | `applied` is a `let` variable mutated inside `setGameState`'s pure updater. Under React 19 StrictMode, the updater runs twice: `applied = true` in the discarded first pass, then on the second pass `(prevState.claimedProgressAchievements || []).includes(achievementId)` may be `false` again (since the first pass was discarded), setting `applied = true` twice. This is benign when both passes commit, but if the first pass commits and the second doesn't (an error in another concurrent update), the global AsyncStorage write at line 2280 runs without an actual state change, potentially double-recording a gold claim. | Use the same pattern as `stateUpdateError`: derive `applied` from the returned state (e.g. check `gameStateRef.current.claimedProgressAchievements.includes(achievementId)` after the state settles). |
| B6 | `services/IAPService.ts:552–555` | **P1** | `initialize()` uses a busy-wait spin loop: `while (this.isInitializing) { await new Promise(resolve => setTimeout(resolve, 100)); }`. If `isInitializing` is stuck `true` (e.g. the `connectAsync()` call hangs without resolving), this loop never exits and consumes the call stack indefinitely. On cold launch this can starve the React render thread. | Replace with a single Promise that resolves when initialization completes, or add a maximum wait timeout (e.g. 10s) that breaks the loop and returns `false`. |
| B7 | `contexts/game/GameActionsContext.tsx:1667–1683` | **P1** | Periodic relationship repair runs `setGameState(prev => repairRelationshipState(prev))` unconditionally when `relValidation.isValid === false`. `repairRelationshipState` returns a new object reference each time (it spreads). This triggers a full re-render every 10 weeks even when no repair was needed if the function's return is never identical to `prev`. More critically, if `repairRelationshipState` has a bug that itself produces an invalid state, this becomes an infinite-repair loop every 10 weeks. | Guard with `if (!relValidation.isValid)` (already there), but additionally check that `repairRelationshipState` actually changed something before calling `setGameState` — compare a key field or pass a `repaired: boolean` return value. |
